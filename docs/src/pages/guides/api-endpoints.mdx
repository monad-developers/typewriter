# Add API endpoints

The handle returned by `createTypewriter` is not a server. You expose the parts
your client needs over HTTP. A client needs four things: the EIP-712 domain to
sign against, a way to submit a signed mutation, a way to read state, and a way to
follow a mutation after it is accepted.

The examples on this page use `Bun.serve` and come from the
[token example](/examples/token).

## Serialize mutation arguments with superjson

Mutation arguments are typed from Solidity, so `uint256` fields are `bigint` in
JavaScript. `JSON.stringify` throws on a `bigint`, and state reads return them, so
plain JSON does not work in either direction.

[superjson](https://github.com/flightcontrolhq/superjson) serializes `bigint`
losslessly and is what both example apps use on the server and the client:

```ts [src/index.ts]
import superjson from "superjson";

function json(data: unknown): Response {
  return new Response(superjson.stringify(data), {
    headers: { "Content-Type": "application/json" },
  });
}
```

Encoding the values as strings by hand also works, as long as the server converts
them back to `bigint` before calling `typewriter.execute`, which is typed against
the mutation's Solidity types.

## Start the runtime, then serve

`createTypewriter` is asynchronous. Await it at the top level of your server file
so the handle exists before the first request arrives.

```ts [src/index.ts]
import { createTypewriter } from "typewriter";
import { privateKeyToAccount } from "viem/accounts";
import Token from "../contracts/src/Token.sol";

const typewriter = await createTypewriter(Token, {
  address: process.env.CONTRACT_ADDRESS as `0x${string}`,
  account: privateKeyToAccount(process.env.SCHEDULER_PRIVATE_KEY as `0x${string}`),
  chainId: Number(process.env.CHAIN_ID),
  rpcUrl: process.env.RPC_URL as string,
  database: { url: process.env.DATABASE_URL as string },
});

const server = Bun.serve({
  routes: {
    // routes go here
  },
});

console.log(`listening on ${server.url}`);
```

## Serve the EIP-712 domain

Clients need the domain to build the typed data they sign. Serve
`typewriter.domain` rather than hardcoding it in the client, so the chain ID and
contract address come from one place.

```ts [src/index.ts]
"/api/domain": () => json(typewriter.domain),
```

The response has the shape
`{ name: "Typewriter", version: "1", chainId, verifyingContract }`.

## Accept mutations

A client posts `{ name, params, signature }`. Pass it to `typewriter.execute`,
which resolves once the mutation is accepted and rejects if it is not.

```ts [src/index.ts]
"/api/mutations": {
  POST: async (req) => {
    const body = superjson.parse(await req.text());
    try {
      const accepted = await typewriter.execute(
        body as Parameters<typeof typewriter.execute>[0],
      );
      return json(accepted);
    } catch (error) {
      return new Response(superjson.stringify({ error: String(error) }), {
        status: 400,
        headers: { "Content-Type": "application/json" },
      });
    }
  },
},
```

The resolved value is `{ id }`, the mutation's ID. Return it: the client needs it
to follow the mutation's status.

A rejection means the contract reverted — a bad signature, a stale nonce, an
insufficient balance. It is a client error, so `400` is the right status. Nothing
is written to state and the mutation never settles.

This endpoint accepts arbitrary input from the network, so validate the body
before trusting it. `typewriter.execute` is typed but does not sanitize; treat
`params` and `signature` as untrusted, exactly as your contract does.

## Read state

`typewriter.state` reads the contract's storage. Field access returns a promise
and mappings are indexed by key, so a route handler can read state directly:

```ts [src/index.ts]
"/api/accounts/:address": async (req) => {
  const account = typewriter.state.accounts[req.params.address as `0x${string}`];
  const [balance, nonce] = await Promise.all([account.balance, account.nonce]);
  return json({ balance, nonce });
},
```

Clients that sign mutations need a nonce endpoint like this one. See
[Read application state](/guides/read-state) for what these reads do and do not
see.

## Stream status updates

`typewriter.on("mutation", callback)` fires every time any mutation changes
status. Subscribe once at startup and keep the latest event per mutation, so a
client that connects after acceptance still gets the current status:

```ts [src/index.ts]
import type { MutationEvent } from "typewriter";

const latest = new Map<number, MutationEvent>();

typewriter.on("mutation", (mutation) => {
  latest.set(mutation.id, mutation);
});
```

Then serve one mutation's status as a server-sent event stream:

```ts [src/index.ts]
"/api/mutations/:id/status": (req) => {
  const id = Number(req.params.id);
  if (!Number.isInteger(id)) return new Response("Bad Request", { status: 400 });

  let unsubscribe = () => {};

  const stream = new ReadableStream({
    start(controller) {
      let last: string | undefined;
      let done = false;

      const send = (mutation: MutationEvent) => {
        if (done || mutation.status === last) return;
        last = mutation.status;
        controller.enqueue(`data: ${JSON.stringify({ status: mutation.status })}\n\n`);
        if (mutation.status === "finalized" || mutation.status === "rejected") {
          done = true;
          unsubscribe();
          latest.delete(id);
          controller.close();
        }
      };

      unsubscribe = typewriter.on("mutation", (mutation) => {
        if (mutation.id === id) send(mutation);
      });

      const current = latest.get(id);
      if (current !== undefined) send(current);
    },
    cancel() {
      unsubscribe();
    },
  });

  return new Response(stream, {
    headers: {
      "Content-Type": "text/event-stream",
      "Cache-Control": "no-cache",
      Connection: "keep-alive",
    },
  });
},
```

Three details matter here. `typewriter.on` returns an unsubscribe function, and a
client that abandons the stream only tells you through `cancel`, so call it in both
places or every disconnected client leaks a listener. Subscribe before replaying the
stored status, so the unsubscribe function exists if that status is already terminal.
And `latest` grows until entries are removed, which the terminal branch above does.

For status meanings, see the [mutation lifecycle](/how-it-works#mutation-lifecycle).
