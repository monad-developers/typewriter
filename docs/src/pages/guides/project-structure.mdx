# Project structure

A Typewriter application is one project with two halves: a Foundry project that
holds the contract, and a Bun server that imports it. Nothing generates or
scaffolds this layout for you, so this page describes what each part is for and
which parts the runtime requires.

```txt
counter/
├── contracts/
│   ├── foundry.toml
│   ├── out/                  # forge build output
│   └── src/
│       ├── Counter.sol       # entrypoint contract
│       ├── Counter.sol.d.ts  # generated by typewriter
│       └── Add.sol           # one library per mutation
├── src/
│   ├── index.ts              # server
│   └── typewriter.d.ts       # declares the *.sol module type
├── .env
└── package.json
```

## `contracts/`

The contract is a normal Foundry project. Three settings in `foundry.toml`
matter to Typewriter:

```toml [contracts/foundry.toml]
[profile.default]
src = "src"
out = "out"
libs = ["../node_modules"]
remappings = ["typewriter/=../node_modules/typewriter/src/"]
extra_output = ["storageLayout"]
```

- **`remappings`** resolves `typewriter/Typewriter.sol` to the installed package.
  This one is required; Foundry's automatic library remapping does not find the
  package's `src` directory through the `node_modules` symlink.
- **`libs`** lets other Solidity packages installed from npm resolve the same way.
- **`extra_output`** emits the storage layout when you run `forge build` yourself.
  The runtime always passes `--extra-output storageLayout` on its own builds, so
  this setting is for your builds, not the runtime's.

One file under `contracts/src/` is the **entrypoint**: the file that declares the
contract inheriting `Typewriter`. Everything else — mutation libraries, the
`State` struct, the `Signature` struct, errors — can live in that file or in files
it imports. The runtime reads the entrypoint and follows its imports.

## `src/`

`src/index.ts` starts the runtime and serves HTTP. It imports the entrypoint
contract by path:

```ts [src/index.ts]
import { createTypewriter } from "typewriter";
import Counter from "../contracts/src/Counter.sol";

const typewriter = await createTypewriter(Counter, config);
```

That import resolves to the file's path, which the runtime compiles and reads.
`src/typewriter.d.ts` tells TypeScript what a `.sol` import is:

```ts [src/typewriter.d.ts]
declare module "*.sol" {
  const entrypoint: import("typewriter").TypewriterSolidityEntrypoint;
  export default entrypoint;
}
```

This file is required. Without it, TypeScript cannot type the import, and the
runtime skips writing the generated declaration described below.

## Generated declarations

When `src/typewriter.d.ts` exists, each startup writes a declaration file next to
the entrypoint — `contracts/src/Counter.sol.d.ts` — containing the contract's
storage layout, mutation tags and parameters, and `Signature` fields as literal
types. The import picks it up automatically, which is what makes the handle typed:

- `typewriter.execute` accepts only your mutation names, with the parameter shape
  each one expects.
- `typewriter.state` has your state's fields and types.
- `typewriter.schema` has one table per mutation, with your parameter columns.

The file is regenerated from the contract, so do not edit it by hand. It is
deterministic, so committing it is safe.

## What the runtime reads at startup

`createTypewriter` runs `forge build --ast --extra-output storageLayout --force`
in the Foundry project, then reads the compiled output:

| From the contract | Used for |
| --- | --- |
| The `Mutation` enum | The tag for each mutation name |
| Each mutation struct decoded in `dispatch` | Mutation parameters, and the columns of its Postgres table |
| The `Signature` struct | The signature fields a client must send, and their columns |
| The storage layout of `state` | Typed state reads |
| The contract ABI | Encoding settlement transactions and decoding force-inclusion events |

Two consequences are easy to miss:

- **Foundry must be installed wherever the server runs**, including in production
  images. The server compiles at startup, not at build time.
- **The Solidity sources must ship with the server**, not just the build output.
  The entrypoint path is resolved and read at runtime.

## Postgres

The runtime creates one Postgres schema per deployment, named
`typewriter_<chainId>_<contractAddress>`, and owns everything in it: a table per
mutation plus its own state tables. Pointing two deployments at the same database
is fine, because their schema names differ. Redeploying the contract to a new
address starts a new schema.

## `package.json`

Nothing in the layout requires specific scripts. These three cover the loop:

```json [package.json]
{
  "scripts": {
    "dev": "bun --hot src/index.ts",
    "start": "bun src/index.ts",
    "contracts:build": "forge build --root contracts"
  }
}
```

`bun --hot` restarts the server on change, which also re-runs the startup
compile — useful while editing the contract.

## Frontends

Typewriter has no opinion about the client. The server is a plain `Bun.serve`
application, so a browser client can be served from the same process with an HTML
import, or from anywhere else. Both example apps serve a React frontend from the
Bun server that runs the runtime. See [Submit mutations](/guides/submit-mutations)
for what the client needs to do.
