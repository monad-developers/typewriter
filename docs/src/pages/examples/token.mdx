# Token

The token app is the smallest practical Typewriter application. It implements two mutations — mint and transfer — for a single ERC-20-style token, and shows how each layer of a Typewriter app fits together: Solidity state and mutation libraries, a Bun HTTP server, and a React frontend.

Source: [apps/token](https://github.com/monad-exp/typewriter/tree/main/apps/token).

## What the app demonstrates

- A `State` struct tracked inside a `Typewriter` contract.
- Two mutation libraries (`MintMutation` and `TransferMutation`) compiled as Solidity libraries and dispatched from the contract.
- EIP-712 typed-data signing for each mutation, verified on-chain.
- Batch sequencing: the server orders mutations so that all `Mint` operations in a batch are settled before `Transfer` operations.
- A server-sent events (SSE) endpoint that streams mutation status from `received` through to `finalized` or `rejected`.
- A browser UI where users sign in by minting tokens to a locally generated key, then transfer to other known addresses.

## Parts walkthrough

### State and mutations

`contracts/src/Token.sol` defines the on-chain state:

```solidity
struct Account {
    uint256 nonce;
    uint256 balance;
}

struct State {
    uint256 totalSupply;
    mapping(address => Account) accounts;
}
```

The `Token` contract extends `Typewriter` and holds a single `State` storage variable. Its `dispatch` function routes incoming mutation bytes to one of two handlers, identified by the `Mutation` enum (`Transfer = 0`, `Mint = 1`).

Each mutation lives in its own Solidity library:

- `contracts/src/Mint.sol` — `MintMutation`. Increases `totalSupply` and the recipient's balance. The signer must be the `to` address.
- `contracts/src/Transfer.sol` — `TransferMutation`. Decreases the sender's balance and increases the recipient's. The signer must be the `from` address.

Both libraries use a shared `verifyTokenSignature` helper in `Token.sol` that checks the EIP-712 digest, validates the per-account nonce, and checks the deadline before accepting a mutation.

For more on writing state and mutations, see [State and mutations](/guides/state-and-mutations).

### Server

`src/index.ts` is the entry point for the Bun server. It calls `createTypewriter` with the compiled `Token` artifact and a configuration object:

```ts
const typewriter = await createTypewriter(Token, {
  address: requireEnv("TOKEN_ADDRESS") as Address,
  account: scheduler,
  chainId: Number(requireEnv("CHAIN_ID")),
  rpcUrl: requireEnv("RPC_URL"),
  database: { url: requireEnv("DATABASE_URL"), maxConnections: 25 },
  sequencing: { order: "batch", batchOrder: ["Mint", "Transfer"] },
});
```

The `sequencing` field sets the mode to `batch` and specifies that `Mint` mutations are settled before `Transfer` mutations within each batch. For details on sequencing options, see [Configuration](/guides/configuration).

The server exposes these HTTP routes:

| Route | Method | Description |
|---|---|---|
| `/` | GET | Serves the frontend HTML |
| `/api` | POST | Accepts a signed mutation and returns its ID |
| `/api/domain` | GET | Returns the EIP-712 domain for client-side signing |
| `/api/addresses` | GET | Returns all known account addresses |
| `/api/account/:address` | GET | Returns balance and nonce for an address |
| `/api/mutation/:id/status` | GET | SSE stream of mutation status updates |

`src/app.ts` exports `signMint` and `signTransfer` helper functions used by both the test suite and the frontend. Each helper calls `signTypedData` via viem, then encodes the `v`, `r`, `s` components into the `TokenSignature` struct the contract expects.

### Frontend

`frontend/App.tsx` is a React component that uses TanStack Query for data fetching. When a user clicks "Sign In", the frontend generates a fresh private key in the browser, mints 1,000 tokens to the new address by calling `POST /api`, and stores the key in `localStorage`. After signing in, the user can transfer tokens to any other address that the server knows about.

The frontend fetches the EIP-712 domain from `/api/domain` on load so it can produce correctly-typed signatures without any hardcoded chain or contract addresses.

## How to run

For full local setup — installing dependencies, configuring environment variables, and starting Anvil — follow [Get started](/guides/get-started).

The app-specific steps, run from `apps/token`, are:

1. Build the contract artifacts:

```bash
bun run contracts:build
```

2. Deploy the token contract:

```bash
bun run deploy
```

3. Start the development server with hot reload:

```bash
bun run dev
```

4. Open the app at `http://localhost:3000`.

To run in production mode without hot reload, use `bun run start` instead of `bun run dev`.

### Environment variables

Copy `apps/token/.env.example` to `apps/token/.env` and set these variables:

| Variable | Description |
|---|---|
| `RPC_URL` | RPC endpoint used by the app and the deploy script |
| `DATABASE_URL` | Postgres connection string |
| `CHAIN_ID` | Chain ID used for EIP-712 typed-data signing |
| `TOKEN_ADDRESS` | Deployed token contract address |
| `PRIVATE_KEY` | Private key for the scheduler account and Foundry broadcast |
